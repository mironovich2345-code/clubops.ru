# Схемы и версии оплаты (STAGE 12)

Схема оплаты — **версионируемая, append-only**. Изменение никогда не редактирует
использованную схему: создаётся **новая версия** с датой начала действия. Прошлые расчёты
(их snapshot) не пересчитываются.

## Два уровня схем
- **Схема категории клуба** — `employeeId = null`, привязана к клубу + должности/категории.
- **Индивидуальная схема сотрудника** — привязана к конкретному сотруднику; **перекрывает**
  схему категории на даты, которые покрывает.

## Версия и логический ключ
Версия инкрементируется в пределах **логического ключа**
`(компания, клуб, сотрудник или «вся категория», должность)` — независимо для категории и для
сотрудника. Не глобальный max. Пример (менеджеры продаж, клуб «Куб»): v1 c 01.01, v2 c 01.08,
v3 c 01.10.

## Статусы
`Черновик → На согласовании → Согласована → Запланирована / Действует → Заменена → В архиве`
(+ `Отклонена / Отменена`). Отклонённые/черновики/отменённые/архивные **не участвуют** в
расчёте. Активность определяется по дате + статусу, а не по возможно устаревшему статусу.

## Даты действия
End-exclusive интервал: `с ≤ дата < по`. При активации новой версии предыдущей открытой
ставится `по = дата новой версии` (она становится «Заменена»). Пример: v1 01.01–31.07, v2
01.08–…. Параметры старой версии **неизменны**; закрывается только интервал.

## Как resolver выбирает версию
По **дате расчётного месяца** (1-е число периода), НЕ по «сегодня». Приоритет: индивидуальная
версия сотрудника → версия категории → «Схема не настроена». Если на дату подходят **две**
живые версии — расчёт блокируется с сообщением «Найдено несколько действующих схем. Требуется
исправление настроек» (не выбираем случайную).

## Snapshot расчёта
При создании расчёта сохраняется: schemeId, version, статус, интервал, логический ключ,
уровень resolver (employee/category/legacy), sourceChangeRequestId, resolvedAt. Новая версия
схемы **не меняет** существующий snapshot — даже открытого периода (silent refresh отсутствует).

## Создание новой версии
1. **Через согласование изменения** (основной путь): регионал предлагает изменение с будущей
   даты → ГД согласует → система **материализует** реальную новую версию (идемпотентно). Если
   материализация не прошла — на карточке заявки кнопка «Создать версию схемы» (повтор безопасен,
   второй версии не будет).
2. **Вручную**: региональный директор создаёт **черновик** версии → «Отправить на согласование»
   → ГД / собственник / гл. бухгалтер «Согласовать и активировать». Регионал сам версию не
   активирует и не редактирует активную in-place.

## Экран «Схемы и версии»
`/payroll/schemes` — список цепочек (клуб, категория/сотрудник, текущая версия, статус, действует
с/по, следующая запланированная, конфликт). Открыть цепочку → история версий + **сравнение**
последних двух (было/стало по параметрам, без сырого JSON) + действия по статусу. Управляющему
раздел недоступен (он видит применённую схему только в расчёте).

## Неизменяемость
Для использованной/активной/заменённой версии заморожены: параметры, категория, сотрудник, клуб,
компания, дата начала, версия, тип схемы. Можно менять только `по` (при корректном supersede),
статус по машине состояний и служебные метки. Черновик — редактируется.
