# Автоматическая синхронизация ОФД — диагностика

Дата: 2026-07-24. Метод: инспекция кода синхронизации + детерминированный прогон
`pilot-ofd-taxcom` (инъекция клиента). Live-прогон против реального Такском требует
действующего подключения и внешнего таймера (инфраструктура) — см. §5.

## 1. Как устроена авто-синхронизация

- Единственная точка входа: `POST /api/cron/ofd/daily`
  (`src/app/api/cron/ofd/daily/route.ts`). Только POST; `force-dynamic`.
- Авторизация (`authorizeOfdCron`, `src/lib/ofd/daily.ts`), fail-closed:
  - не POST → **405**; `OFD_INTEGRATIONS_ENABLED` не включён → **503**;
  - `CRON_SECRET` не задан → **503**; неверный секрет → **401**.
  - Принимает `Authorization: Bearer <CRON_SECRET>` или `X-Cron-Secret`.
- Логика: `runDailyOfdImport` → `runOfdImportBatch` по всем `OfdConnection`
  `{ provider:"taxcom", isActive:true }`, импорт **вчера** (server-local день),
  режим `auto_daily`. Изоляция по подключению: падение одного не останавливает
  остальные (try/catch в цикле, ошибка → безопасный код в `OfdSyncError`).
- Идемпотентность: чеки дедуп по `OfdReceiptImport.dedupeKey @unique`
  (`taxcom:ФН:ФД[:ФПД]`), позиции по `itemKey`. Повторный запуск не создаёт дублей.

## 2. Первопричина (почему авто-синхронизация могла не работать)

**В репозитории НЕТ планировщика.** Нет `vercel.json`; деплой — Railway/Docker.
Route `/api/cron/ofd/daily` обязан вызываться **внешним** systemd-таймером/cron
(описано в `docs/RU_DEPLOYMENT.md`). Ранжирование причин:

1. **Внешний таймер не настроен на проде** → route никогда не вызывается. **Самая
   вероятная причина.**
2. **`OFD_INTEGRATIONS_ENABLED` не выставлен** → route отвечает 503, ничего не
   импортируется. (Флаг выключен по умолчанию.)
3. **`CRON_SECRET` не задан / не совпадает** → 503 / 401.
4. **Часовой пояс сервера ≠ МСК.** «Вчера» считается по server-local дню (per-club
   TZ в системе нет). Если сервер в UTC, запуск в 00:00 может импортировать не тот
   день; плюс Такском отдаёт вчерашние чеки с задержкой (~00:05–00:10 МСК).
5. **Пагинация:** клиент шлёт `pn=1, ps=100` без цикла — >100 чеков/смену или >100
   смен/день **молча обрезаются** (`src/lib/ofd/taxcom/client.ts`). Известное
   ограничение (см. §6), не влияет на клубы с малым числом чеков.

Токен Такском создаётся лениво на каждый запуск (Login по требованию) — истечение
токена между запусками не является постоянной причиной сбоя.

## 3. Health-статус (наблюдаемость)

Добавлен `loadOfdSyncStatus` (`src/lib/ofd/health.ts`), выводит состояние из
`OfdSyncRun` + активных подключений (безопасные коды, без сырого текста ошибок):
`healthy | delayed | failed | never_synced | running | disabled`. Отображается на
дашборде (блок «Данные ОФД», Этап 3): последняя успешная / последний запуск /
провайдер / подключения / загружено-новых. `delayed` = последний успех старше ~30 ч
(дневная синхронизация не проходила).

## 4. Устойчивость (что уже обеспечено)

- Каждое подключение обрабатывается независимо; ошибка одного не рушит остальные.
- Идемпотентность (dedupeKey/itemKey) — повторный запуск без дублей.
- Fail-closed авторизация cron.
- Per-connection lock импортёра (`already_running`) — нет параллельного импорта того
  же подключения.
- Безопасные логи/ответы (никаких секретов/PII/стеков).

## 5. Проверка

### 5.1 Детерминированная (выполнена, зелёная)
`npm run pilot:ofd-taxcom` — мирроринг `lib/ofd/*` с **инъекцией** клиента
(`ImportParams.clientFactory`/`fetchImpl`, `RunDailyOptions.listConnections/importer`):
проверяет нормализацию + дедуп (идемпотентность), пересчёт дневных/категорийных
агрегатов, day-batching, роль-гейт, отсутствие PII/логов. Это доказывает корректность
самого механизма импорта БЕЗ реального Такском. `npm run pilot:ofd-sync-dashboard`
проверяет деривацию health-статуса по всем состояниям.

### 5.2 Live (требует инфраструктуры — НЕ выполнено здесь)
Требуется действующее подключение Такском + настроенный таймер. Шаги:
1. Ручной sync тестового подключения (кнопка на дашборде/в настройках).
2. Запуск ТЕМ ЖЕ entrypoint, что использует cron: `POST /api/cron/ofd/daily` с
   `Authorization: Bearer <CRON_SECRET>`.
3. Проверить новые `OfdReceiptImport` + `OfdReceiptItem` + `OfdDailySalesSummary`.
4. Проверить дашборд/аналитику.
5. Повторный запуск → отсутствие дублей (dedupeKey).
6. Искусственная ошибка авторизации (неверные креды одного подключения) → безопасный
   код, остальные подключения продолжают.
7. Искусственная временная ошибка → восстановление на следующем запуске.

## 6. Известные ограничения / рекомендации

- **Настроить внешний таймер** на прод: systemd `OnCalendar` или платформенный cron,
  POST на `/api/cron/ofd/daily` ~00:15 МСК с `CRON_SECRET`. Выставить
  `OFD_INTEGRATIONS_ENABLED=true`, `OFD_SECRET` (≥32), `CRON_SECRET`.
- **Часовой пояс:** запускать по МСК (или сервер `TZ=Europe/Moscow`), чтобы «вчера»
  совпадало с календарём клуба и учитывало задержку публикации чеков.
- **Пагинация (follow-up):** реализовать постраничный обход `pn` до страницы < `ps`
  в `listShifts`/`listDocumentsByShift`. Сейчас НЕ меняется, т.к. точную семантику
  пагинации Такском нужно подтвердить на реальном API (не угадывать контракт).
  Для клубов с >100 чеков/смену — риск недобора; отслеживать по расхождению с
  «Фактическими деньгами» (Этап 2).

## 7. Вывод

Механизм импорта корректен и идемпотентен (детерминированно подтверждено). Наиболее
вероятная причина «авто-синхронизация не работает» — **инфраструктурная**: не
настроен внешний таймер и/или не заданы `OFD_INTEGRATIONS_ENABLED`/`CRON_SECRET`.
Health-статус теперь виден на дашборде. Live-доказательство работы требует настройки
таймера и реального подключения (см. §5.2).
