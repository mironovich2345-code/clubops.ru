# Астрал.ОФД — discovery

**Статус интеграции: BLOCKED BY DOCUMENTATION + BLOCKED BY ACCESS.**

По правилу №7 интеграция НЕ считается готовой, пока не выполнен реальный запрос с
действующими реквизитами и не получены реальные данные. В текущей среде **нет** доступа к
официальному кабинету Астрал.ОФД, API-ключа, идентификатора организации и официальной
документации, поэтому endpoints/авторизация **не подтверждены** и live-запрос не выполнялся.

Что реализовано сейчас (Этап 5): провайдер-абстракция + Taxcom-адаптер (live) + **skeleton
Астрал** с **предварительным** нормализатором чеков и honest `testConnection`, который
отказывает, а не притворяется. Ниже — что нужно уточнить и получить, чтобы довести до live.

## 1. Что нужно проверить (официально)

Источник истины — только официальный кабинет/документация Астрал.ОФД и договорные условия
владельца аккаунта. **Не** использовать старые неофициальные примеры как production-контракт.

- Есть ли API в тарифе/аккаунте; где выпускается API-ключ.
- Базовый URL; тип авторизации; срок жизни токена.
- Endpoints: кассы; смены; фискальные документы.
- Пагинация; фильтры по дате; формат временных зон; лимиты; retry; коды ошибок.
- Формат чека и позиций; признаки: приход / возврат прихода / коррекция; наличные /
  электронные; ФН / ФД / ФП(FiscalSign); рег. номер ККТ; ИНН; типы оплаты; наименования
  товаров; НДС; смены; отменённые документы; единицы сумм (копейки или рубли — критично).

## 2. Подтверждённые endpoints / auth

**Нет.** Требуется официальная документация. Ничего не выдумываем как контракт.

## 3. Необходимые секреты

- API-ключ / логин-пароль Астрал.ОФД (хранить AES-256-GCM в `OfdConnection.*Encrypted`,
  как для Такском; в UI — только masked).
- Идентификатор организации / список ФН касс.
- Базовый URL (в `OfdConnection.serverBaseUrl`).

## 4. Маппинг в текущую OFD-модель (ПРЕДВАРИТЕЛЬНО — подтвердить!)

Целевой нормализованный DTO — общий для всех провайдеров: `NormalizedOfdReceipt`
(`src/lib/ofd/types.ts`). Провайдер обязан выдавать именно его, тогда все агрегаты/аналитика
работают без изменений. Предварительное соответствие (реализовано в
`src/lib/ofd/providers/astral-provider.ts:mapAstralReceipt`, поля — гипотеза):

| NormalizedOfdReceipt | Astral (провизорно) | Примечание |
|---|---|---|
| fnNumber | fn / fnNumber | ФН |
| fiscalDocumentNumber | fd / fiscalDocumentNumber | ФД (Int) |
| fiscalSign | fp / fiscalSign | ФП/ФПД |
| operationType | operationType/type (1/приход, 2/возврат) | → income \| income_return |
| receiptDate | dateTime / receiptDate / date | ISO → Date |
| totalKopeks / cashKopeks / electronicKopeks | totalSum / cashSum / ecashSum | **единицы (коп/руб) уточнить!** |
| items[] | items[{name,price,quantity,sum}] | name/price(коп)/qty(→milli)/sum |
| dedupeKey | — | генерируется: `astral:ФН:ФД[:ФП]` (не пересечётся с taxcom) |

## 5. Отличия от Такском

- Такском: `serverBaseUrl` per-connection, lazy Login → Session-Token + Integrator-ID,
  `dedupeKey = taxcom:ФН:ФД[:ФПД]`, позиции по тегам ФФД (1030/1023/1079/1043).
- Астрал: авторизация/формат **не подтверждены** — вероятно другой auth (API-key?),
  другой JSON позиций. Нормализатор изолирует эти различия; downstream не меняется.

## 6. Блокеры (что нужно от пользователя/Астрал)

1. Действующий аккаунт Астрал.ОФД с включённым API и тарифом, дающим доступ к API.
2. API-ключ/логин + базовый URL + идентификатор организации + список ФН касс.
3. Официальная документация API (endpoints, auth, пагинация, коды ошибок, формат чека/
   позиций, единицы сумм, временные зоны).
4. Тестовая организация/период для сверки малого диапазона (кол-во чеков и суммы: всего /
   наличные / электронные / возвраты) с кабинетом Астрал.

## 7. План доведения до live (после разблокировки)

1. Подтвердить контракт по §1 из официальных материалов; обновить `mapAstralReceipt` и
   `AstralProvider.testConnection` под реальные endpoints/auth.
2. Реализовать пагинацию + фильтр по дате + временные зоны как у реального API.
3. `testConnection` — реальный минимальный запрос (организация/кассы), без импорта.
4. Импорт малого подтверждённого периода → сверка кол-ва/сумм/номенклатуры с кабинетом.
5. Повторная синхронизация → проверка отсутствия дублей (dedupeKey).
6. Проверка dashboard/analytics.
7. Массовую синхронизацию — только после сверки малого диапазона.

Только после успешного п.3–5 с реальными данными статус меняется на **LIVE**.
