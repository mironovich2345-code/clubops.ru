## 1. Что реализовано

1. **Фактические деньги (сверка наличных)** — ежедневное подтверждение управляющим
   пересчитанных наличных отдельно по ООО/ИП, с дедлайном, расхождением, разбором.
2. **Быстрая синхронизация ОФД на дашборде** — блок «Данные ОФД» + кнопка, повторно
   использующая существующий sync-сервис.
3. **ПИН критических настроек** — отдельный (не пароль) bcrypt-ПИН + короткоживущая
   verification session, гейтит чувствительные действия.
4. **Астрал.ОФД foundation** — провайдер-абстракция + Taxcom-адаптер (live) + Astral
   skeleton + discovery-док (статус BLOCKED).
5. **Диагностика загрузки документов возврата** — первопричина устранена, точные коды
   и сообщения, наблюдаемость.
6. **Диагностика авто-синхронизации ОФД** + health-статус.

## 2. Что исправлено

- **Загрузка возвратов:** первопричина — не задан `serverActions.bodySizeLimit`
  (дефолт ~1 МБ < 10 МБ) → файл 1–10 МБ отклонялся Next до обработчика → голый catch
  «Ошибка загрузки». Исправлено (bodySizeLimit=20mb) + структурные коды + сообщения +
  reference id + observability.
- **Авто-синхронизация ОФД:** диагностирована первопричина (нет внешнего таймера /
  env), добавлен health-статус и honest-доку; механизм импорта подтверждён
  детерминированно.

## 3. Где размещены «Фактические деньги»

На `/collections` (раздел «Инкассация») — блок «Фактические деньги (сверка наличных)»:
форма per-entity (по ОФД / ожидаемый остаток / факт / расхождение / комментарий при
расхождении) + история сверок с подсветкой просрочки/расхождения и review-кнопками.
Выбрано это место, т.к. страница уже владеет карточками ООО/ИП и «Контрольным
остатком». Модель `DailyCashReconciliation` (скалярные id, kopeks, unique
clubId+legalEntityId+businessDate) — запись-подтверждение, деньги НЕ двигаются.

## 4. Дедлайн до 12:00

`reconciliationDeadline(businessDate)` = 12:00 следующего дня (server-local — per-club
TZ в системе нет, зафиксировано). `isReconciliationOverdue` = ещё «ожидает» и прошёл
дедлайн; `submittedOnTime` = подтверждено не позже дедлайна. Просрочка подсвечивается в
истории; при расхождении регионалу уходит уведомление (outbox). Система не
блокируется.

## 5. Как сверяется ОФД и фактический остаток

`buildReconciliationTargets` берёт ожидаемый остаток и OFD-наличные из существующего
`loadClubCashBalances` (`cash{Ooo,Ip}FactBalance`, `cash{Ooo,Ip}OfdYesterday`) — БЕЗ
параллельного расчёта. `difference = actual − expected`. При `difference != 0` —
обязательны причина (справочник из 10 кодов) + комментарий; статус `discrepancy` →
разбор регионалом → закрытие бухгалтером. ОФД не переписывается; авто-корректировок
кассы нет.

## 6. Какие роли видят кнопку синхронизации

Блок «Данные ОФД» — роли, видящие ОФД-продажи (owner/GD/regional) ИЛИ имеющие право
запуска. Право запуска — новая **server-side** capability `ofd.sync.trigger`:
owner / general_director / regional_director / accountant / chief_accountant (НЕ
manager, НЕ marketer). `companyId` берётся только из своего контекста (нельзя
синхронизировать чужую компанию). Повтор блокируется общим rate-limit
(`ofd_sync_now`/company, 1/5мин) + per-connection lock импортёра. Аудит
`ofd.sync_now` (source: dashboard).

## 7. Как защищены настройки

Отдельный ПИН компании (`Company.settingsPinHash`, bcrypt — НЕ пароль пользователя,
сравнение только с `settingsPinHash`). Верный ПИН → короткоживущая server-side
verification session (httpOnly cookie + `SettingsPinSession`, только HMAC токена,
TTL 15 мин). Блокировка после 5 неверных попыток + rate-limit `settings_pin`.
`requireSettingsPin` — **opt-in** guard: пока ПИН не задан, поведение не меняется;
после — критичное действие требует подтверждения. Подключён к `saveOfdConnection`
(секреты ОФД); расширяется на прочие критичные действия одной строкой. Аудит
pin_set/verified/failed.

## 8. Как работает invited owner

Первичный собственник — явное поле `Company.primaryOwnerUserId` (задаётся при создании
компании; бэкофилл существующих = самый ранний OWNER-доступ, НЕ «самый старый
пользователь»). **Первичный** собственник задаёт/меняет ПИН (при смене нужен текущий
ПИН). **Приглашённый** собственник вводит общий ПИН компании для доступа к защищённым
настройкам, но НЕ видит и НЕ меняет ПИН без прав первичного собственника; пароль
пригласившего недоступен и не используется для проверки.

## 11. Причина ошибок загрузки документов возврата

Две точки схлопывания: клиент `RefundDraftEditor.tsx` — голый `catch { setError("Ошибка
загрузки.") }` (проглатывал любую брошенную ошибку без кода/лога); сервер — все сбои
storage в один `STORAGE_FAILED`. Триггер — латентная ловушка: без
`serverActions.bodySizeLimit` Next отклонял тело >~1 МБ до обработчика.

## 12. Новые пользовательские сообщения об ошибках

Коды: `HEIC_UNSUPPORTED` (совет сохранить как JPG/PDF), `STORAGE_UNAVAILABLE`,
`STORAGE_WRITE_FAILED`, `DATABASE_WRITE_FAILED`, `DUPLICATE_FILE`, `REQUEST_TOO_LARGE`,
`UPLOAD_TIMEOUT`, `NETWORK_ERROR`, `UNKNOWN_UPLOAD_ERROR`. Клиент даёт понятный текст
(крупный файл → «максимум 10 МБ»; иначе — сеть/размер запроса). Ошибке присваивается
короткий reference id (для поддержки); server-log структурный, без содержимого файла.
HEIC определяется по байтам (ftyp brand). Дубликат (тот же sha256 в другом слоте)
отклоняется.

## 13. Причина сбоя автоматической синхронизации

Инфраструктурная: в репозитории НЕТ планировщика — `POST /api/cron/ofd/daily` должен
вызываться внешним systemd-таймером/cron. Если таймер не настроен или не заданы
`OFD_INTEGRATIONS_ENABLED`/`CRON_SECRET` (→503) — авто-синк не запускается. Вторично:
server-local «вчера» vs МСК + задержка публикации чеков; пагинация ps=100 без цикла.
Подробно — `docs/testing/ofd-sync-diagnostics.md`.

## 18. Реструктуризация настроек ОФД (follow-up, ветка `feat/ofd-unified-settings`)

синхронизации: обзор — read-only агрегация существующих `OfdConnection` /

**Маршруты:**

| URL | Назначение | Доступ |
|---|---|---|
| `Настройки → Интеграции` | одна кнопка **«Подключение ОФД»** → `/settings/ofd` | owner / GD |
| `/settings/ofd` | обзор: карточки провайдеров (Такском / Астрал) со статусом, кол-вом организаций/касс, последней синхронизацией | owner / GD (server-side, иначе redirect) |
| `/settings/integrations/ofd` | экран Такском (без изменений; **старый URL сохранён — не 404**) | owner / GD |
| `/settings/ofd/astral` | пошаговый экран Астрал: Шаг 1 (API-ключ, masked, PIN-gated) + Шаги 2–5 заготовки | owner / GD |

**Обратная совместимость:** все server-actions Такском, права, dashboard-sync и cron

## 20. Такском: один кабинет = одно подключение с кассами разных юрлиц (ветка `fix/taxcom-multi-kkt-connections`)

**Первопричина (по коду):** импорт выбирал кассы по `legalEntityId` подключения; юрлицо
кассы наследовалось от подключения; создание подключения плодило по одному `OfdConnection`
на юрлицо. Кабинет с двумя кассами разных клубов разъезжался на «Такском» (legalEntityId=null)
и «Такском · ПИТЕР СПОРТ», а синхронизация показывала только Союз (фильтр по юрлицу исключал
кассу Куб без юрлица).

**Исправление:**
- **Импортер** (`importer.ts`): кассы выбираются по кабинету (`companyId+provider`), **без**
  фильтра по `legalEntity` подключения; юрлицо — **только из кассы** (`mapping.legalEntityId`,
  без наследования); касса без юрлица не идёт в финансовые агрегаты (`ofd_kkt_requires_legal_entity`,
  partial-статус); результат содержит **разрез по клубам** (`perClub`) + `unboundKkts`.
- **Создание подключения** (`actions.ts`): дедуп по кабинету (необратимый sha256-fingerprint
  `serverBaseUrl|authType|credential`, секрет не логируется) — второе подключение к тому же
  кабинету создать нельзя; другое юрлицо больше **не** повод для нового подключения. Юрлицо
  кассы выбирается **при добавлении кассы**; новое действие `updateOfdMapping` — «указать/
