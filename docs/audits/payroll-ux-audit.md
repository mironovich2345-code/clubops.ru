# Аудит UX модуля «Зарплата (ФОТ)»

Аудит фактического UI **до** изменений. Цель — упростить процесс, разделить
начисление / согласование / выплату и вынести авансы в отдельный раздел, не трогая
расчётный движок, статусы, права и финансовую логику. Ниже — по каждому экрану:
что видно, действия, что перегружает, где смешаны этапы, что спрятано, ручное vs
авто, опасные действия.

## Карта маршрутов (факт)

| Маршрут | Файл | Роль экрана |
|---|---|---|
| `/payroll` | `page.tsx` | **технический список** сотрудников + текущая схема |
| `/payroll/periods` | `periods/page.tsx` | список периодов + форма создания |
| `/payroll/periods/[id]` | `periods/[id]/page.tsx` | детали периода — **все расчёты стопкой** |
| `/payroll/employees/[id]` | `employees/[id]/page.tsx` | настройка сотрудника + **создание аванса** + долги |
| `/payroll/obligations` | `obligations/page.tsx` | долги/обязательства (погашение) |
| `/payroll/regional` | `regional/page.tsx` | расчёт регионала по городу |
| `/payroll/summary` | `summary/page.tsx` | сводка ФОТ |

Навигация между разделами — только через 4 кнопки в шапке `/payroll` (Сводка, Регионал,
Долги, Расчётные периоды). Единого горизонтального меню нет.

## 1. `/payroll` — главная

- **Видно:** таблица активных сотрудников (ФИО, клуб, должность, закрепления, текущая
  схема-чип, кнопка «Открыть»). Шапка с 4 кнопками-ссылками.
- **Действия:** открыть карточку сотрудника; перейти в Сводку/Регионал/Долги/Периоды.
- **Перегружает:** это **не обзор**, а плоский список схем. Нет KPI, нет «что делать
  дальше», нет статуса процесса, нет авансов/выплат/долгов сводно.
- **Смешение этапов:** нет разделения «настройка / начисление / выплата».
- **Спрятано:** периоды, авансы, выплаты, проблемы — за кнопками/вглубь.
- **Ручное/авто:** схема резолвится авто (`resolveEffectiveScheme`); всё read-only.
- **Опасное:** нет.

## 2. `/payroll/periods` — список периодов

- **Видно:** форма «Создать период» (клуб + месяц) сверху; таблица: Клуб, Месяц, Статус
  (серый чип), Сотрудников, Начислено, «Открыть».
- **Действия:** создать период (`CreatePeriodForm`), открыть период.
- **Перегружает:** статусы — одинаковый серый чип, визуально не разделены; нет колонок
  Выплачено/Остаток/Проблем; нет фильтров (месяц/клуб/статус/проблемные).
- **Смешение:** нет.
- **Спрятано:** создание — простая форма без предпросмотра (§5 просит мини-мастер с
  «сотрудников найдено / без схемы / с ошибками» до создания).
- **Ручное/авто:** суммы авто (`groupBy`).
- **Опасное:** период создаётся «молча», даже если часть сотрудников без схемы — без
  предупреждения заранее.

## 3. `/payroll/periods/[id]` — детали периода ⚠ ГЛАВНАЯ ПРОБЛЕМА

- **Видно:** тоталы (Сотрудников/Начислено/К выплате/Требуют решения), панель согласования
  (`PeriodWorkflowBar`), кнопка «Сформировать состав», затем **для КАЖДОГО сотрудника
  сразу развёрнуты**: `CalculationCard` (исходные данные + расшифровка), `AdjustmentsSection`
  (корректировки), `TrainerPackages` (для тренеров), `PaymentsSection` (выплаты + форма
  аванса).
- **Действия:** рассчитать/сохранить/согласовать/утвердить (workflow), ввод смен/часов/
  продаж, добавить премию/удержание, выплатить, выдать аванс, отменить выплату/аванс.
- **Перегружает:** **всё раскрыто одновременно** — на 10 сотрудников это 10× (входные поля
  + расшифровка + корректировки + выплаты + аванс). Огромная простыня, горизонтальный скролл
  форм на мобильном.
- **Смешение этапов:** в одной карточке смешаны **исходные данные + начисление +
  корректировки + выплаты + аванс** — нет разделения «начисление → согласование → выплата».
- **Спрятано:** нет краткого/подробного режима; нельзя свернуть.
- **Ручное/авто:** входные поля (смены/часы/продажи) — ручные, но подставляются из ОФД/плана
  (источник не подписан у поля); расшифровка — авто.
- **Опасное:** выплата/аванс/отмена — есть `window.confirm` на отменах; форма выплаты
  показывается всегда при `payable` (не отделена по статусу как отдельный шаг).

## 4. `/payroll/employees/[id]` — настройка сотрудника ⚠ АВАНС СПРЯТАН ЗДЕСЬ

- **Видно:** Платёжный профиль, Закрепления, Схемы оплаты (история + форма), **Авансы**
  (`EmployeeAdvancePanel` — список + **форма выдачи аванса**), Долги/обязательства.
- **Действия:** правка профиля/закреплений/схем; **создание аванса** (месяц, сумма, способ,
  заработано-к-дате вручную, комментарий); подтверждение аванса регионалом; отмена аванса.
- **Перегружает:** 5 крупных секций на одной странице; аванс — глубоко внизу.
- **Смешение:** настройка сотрудника + денежная операция (аванс) + долги на одном экране.
- **Спрятано:** **аванс создаётся только отсюда** — из глубины карточки сотрудника (нарушает
  требование §8: аванс часто до периода и должен быть отдельным разделом). Нет отдельного
  `/payroll/advances`.
- **Ручное/авто:** «Заработано к дате» — ручное (требует комментарий, подтверждение
  регионала); при наличии расчёта — авто из `netPayableKopeks`.
- **Опасное:** выдача наличного аванса = движение кассы; отмена = сторно расхода (есть
  `confirm`).

## 5. `/payroll/obligations` — долги

- **Видно/действия:** список обязательств (`ObligationRow`), погашение. Отдельный экран,
  доступен из шапки/карточки сотрудника.
- **Перегружает/смешение:** приемлемо; в целевую навигацию войдёт как «Долги».

## 6. `/payroll/regional` — регионал

- **Видно/действия:** единый расчёт регионала по городу (`RegionalCityForms`). Отдельный
  экран. В целевую навигацию — «Регионал».

## 7. `/payroll/summary` — сводка ФОТ

- **Видно/действия:** агрегаты ФОТ. Частично дублирует будущий «Обзор» — обзор должен стать
  главной, summary можно оставить как расширенную аналитику или влить в обзор.

## Дублирование аванса (важно для §14/§20)

Есть **два** механизма «аванс»:
1. **Pre-period** — модель `PayrollAdvance`, `advance-actions.ts`
   (`recordEmployeeAdvance`/`approveEmployeeAdvance`/`cancelEmployeeAdvance`),
   UI `EmployeeAdvancePanel`. Полный процесс: `requested → (regional approve) → paid`,
   salary expense (`kind:"advance"`) + движение кассы, дедуп по (employee, club, year,
   month), авто-связь с расчётом через `findMonthCalc` + `recomputeCalculationTotals`
   (без повторного расхода).
2. **In-card** — `recordAdvance`/`cancelAdvance` в `periods/actions.ts`, UI внутри
   `PaymentsSection` (форма «Аванс» рядом с «Выплатить»). Период читает `paidAdvances`
   (модель `PayrollAdvance`, status `paid`) → `advByEmployee` и показывает как read-only
   строку + отмена.

**Вывод:** основным должен стать раздел `/payroll/advances` над механизмом (1); в карточке
расчёта (`PaymentsSection`) форму создания аванса убрать → оставить read-only summary +
ссылку (§7.5). Никакой второй бизнес-логики не вводить.

## Мобильная версия

- Таблицы со скроллом по горизонтали; на `/payroll/periods/[id]` формы (выплаты/аванс/
  корректировки) плохо помещаются. Кнопки согласования тонут в простыне. Нужны карточки
  вместо таблиц, компактная шапка, краткий режим по умолчанию.

## Что менять (резюме, без правки движка)

1. `/payroll` → **Обзор** (KPI + «Требуют внимания») + горизонтальное меню.
2. Компактный список периодов с фильтрами и разделёнными статусами; мастер создания с
   предпросмотром.
3. Компактный ростер периода + **страница расчёта сотрудника**
   `/payroll/periods/[id]/employees/[calculationId]` (краткий режим по умолчанию).
4. Новый раздел **`/payroll/advances`** (список + создание, независимо от периода).
5. Раздел **`/payroll/payments`** (движение денег отдельно от начисления).
6. В карточке расчёта: аванс — только summary + ссылка.
7. Блок «Требуют решения» с прямыми ссылками на действия.
8. Мобильные карточки, тесты, документация.

Движок (`src/lib/payroll/*`), статусы, права, создание salary expense, движения кассы,
долги, дедуп авансов, tenant isolation и существующие payroll-тесты — **не менять**;
UI становится оболочкой над ними.
